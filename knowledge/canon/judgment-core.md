# 판단 코어 (Judgment Core) — modfolio 부품 규격

> **오너 요구 (2026-08-23)**: *"어디에든 끼워 넣을 수 있는? 커스터마이징 할 수 있는?
> 약간 부품세트처럼, 우리도 modfolio 기술 세트를 만들었으면 좋겠는데."*

여섯 repo 가 **조율 없이** 2026-08 에 각자 자기 도메인의 부품을 지었는데 **여섯 개가 같은
형태**로 나왔다. 이 문서는 그 형태를 발견해서 이름 붙인 것이지, 새로 발명한 규칙이 아니다.

## 형태

```
부품(판단 코어)   순수 판단.  I/O 0 · 상태 0 · 시계 안 읽음 · 의존 zod 하나 · $0
소비(셸)          바이트를 옮기고 · LLM 을 부르고 · DB 를 치고 · 파일을 지운다
```

- `@modfolio/erasure-proof` 는 **삭제를 안 한다** — 되물어 판정만 한다
- `@modfolio/document-convert` 는 **변환을 안 한다** — 받아들일지 판정한다
- `@modfolio/audio-assembly` 는 **바이트를 안 만진다** — 조립 계획을 내고 검증한다
- `@modfolio/deadline-feed` 는 **원천을 안 읽는다** — 급함·정렬·앵커만 정한다

산업 이름은 **functional core, imperative shell** 이다(Gary Bernhardt). 우리가 그 이름을
보고 만든 것이 아니라, 여섯 번 짓고 나서 같은 것에 도달했다.

## 왜 이 형태가 오너의 요구를 만족시키는가

| 요구 | 순수 판단이면 자동으로 따라온다 |
|---|---|
| **어디에든 끼워 넣는다** | 무거운 의존이 없다 — edge · node · 브라우저 · 테스트 어디서나 |
| **커스터마이징된다** | 정책을 **인자로** 받는다. `UrgencyPolicy`·`ReliabilityThresholds` 는 도메인 판단 값에 기본값을 두지 않는다 |
| **겹치지 않는다** | I/O 가 없으면 **남의 도메인에 닿을 수단이 없다** |
| 버전 업데이트에 안 흔들린다 | 상류 breaking 이 올 상류가 없다 |
| 대조쌍이 항상 가능 | 네트워크를 안 탄다 — 「마감 1시간 전」을 단언할 수 있다 |
| 원가 0 | 랩 패널 9개가 전부 $0 인 것이 우연이 아니다 |

**세 번째 줄이 「각 프로젝트가 겹치지 않게」에 대한 구조적 답이다.** 규칙으로 겹침을
금지하는 것이 아니라 **겹칠 수단을 주지 않는 것**이다. 규칙은 세션마다 흔들리고 구조는
안 흔들린다 — 이 저장소가 [[instruction-drift]] 에서 실측한 그대로다.

## 규격 — `bun run part:spec` 이 검사한다

| | 검사 | 왜 |
|---|---|---|
| ① | **순수** — `node:*` · `fetch(` · `process.env` · `Date.now()` · 무인자 `new Date()` · `Math.random()` 0건 | 세상을 만지지 않는다. 시계·난수가 들어가면 그 분기는 **작성되고 한 번도 실행되지 않는다** |
| ② | **의존** — `dependencies` ⊆ `{zod}` | 어휘 하나. 나머지는 소비자의 것 |
| ③ | **대조쌍** — `*.test.ts` 가 있고 `expect()` 가 0건이 아니다 | 게이트 없는 부품은 주장이다 |
| ④ | **선언** — 그 repo 의 `platform-adapter.json` 이 `provides` 로 선언 | atlas 가 조인한다 |

### ★ 모집단은 **랩이 당기는 것**이다 — 모든 `@modfolio/*` 가 아니다

`assembly-law.md` §1 은 3표면(**contracts · MCP · endpoint**)을 **메뉴**로 규정한다.
판단 코어는 **contracts 표면의 규격**이고, `pay-sdk` 같은 HTTP 클라이언트는 **endpoint
표면**이다. `fetch()` 는 그 패키지의 결함이 아니라 **존재 이유**다.

⚠ 이 게이트의 초판이 정확히 그 구분을 놓쳐 첫 실행에 **19개 중 13개**를 빨갛게 만들었고,
그 13개는 대부분 **정당한 코드**였다. 「canon 을 *더* 집행하면 규약 준수를 벌한다」의
재현이다. 모집단은 `modfolio-dev`(랩)이 참조하는 패키지로 좁혔다 — 계획 §3 이 이미
*"패널 없는 부품은 미완성"* 이라고 정의했기 때문이다.

## 여섯 단계 — 부품 하나를 끝내는 정의

```
① 구축      순수 판단으로. 도메인의 진짜 판단 하나
② 대조쌍    결함 입력 → 실패 · 정상 입력 → 통과. **결함은 원 사건에서** (합성 금지)
③ 게시      pkg.modfolio.io — @modfolio 스코프
④ 콜드설치  소비자 헤더로 확인 (전파 지연 ≠ 실패 — 창을 준다)
⑤ 선언      platform-adapter.json 의 provides
⑥ 랩 패널   modfolio-dev 에 패널 — **이게 「당겨진다」의 유일한 증거**
```

⑥이 없으면 「지어뒀다」와 「아무도 안 쓴다」가 구분되지 않는다. 이 저장소가 반복해 기록한
**「인바운드 0 = 문이 없다」**.

## ★ 대조쌍 다음 — **속성**(2026-08-24 추가)

규격 ③은 「대조쌍이 있다」까지만 본다. 그걸로 부족한 부품 부류가 있다:

> **뒤집어도 아무것도 안 깨지는 불변식은 테스트가 유일한 방어다.**

플래그 판정이 잘못 꺼지면 기능이 안 보일 뿐이고, 잘못 켜지면 **아무도 그것을 «버그» 로
신고하지 않는다.** 쿼터 판정의 미측정 축이 조용히 `ok` 로 그려져도 화면은 초록이고,
한도를 실제로 넘는 날까지 아무도 모른다 — **2026-08-23 에 그게 일어났다**(Neon
data-transfer 쿼터가 야간 백업을 막았다).

이 부류에서 예시 테스트는 **내가 생각해 낸 입력**만 본다. 그리고 결함은 대개 생각하지
못한 자리에 있다. 이 저장소는 그 편향에 이미 이름을 붙여 뒀다:

> *"합성 결함을 만들 때 우리는 가드의 패턴을 먼저 읽는다. 그래서 패턴의 좁음이 대조쌍에
> 그대로 복제된다."* — `agent-evidence.md` §대조쌍 ②

**판단 코어는 속성 테스트의 이상적 대상이다** — 순수하고, I/O 가 없고, 정책이 인자다.
네트워크도 픽스처도 필요 없으므로 수천 회 실행이 초 단위로 끝난다.

### 무엇을 속성으로 쓰는가 — 이것이 설계의 전부다

「출력이 맞다」는 속성이 **아니다**(그건 오라클이 필요하다). 쓰는 것은
**뒤집히면 도메인이 깨지는 단방향 함의**다. 허브 부품 2종에서 실제로 쓴 것:

```
rollout 단조성       비율을 올렸는데 켜져 있던 사람이 꺼지면 램프가 사고가 된다
킬스위치 지배        사고 대응에서 다른 무엇도 이것을 이기면 안 된다
unknown ≠ off        오타를 조용한 기능 소실로 만들지 않는다
교차 실험 독립성     유닛만 해싱하면 한 번 실험군이 영원히 모든 실험군이 된다
미측정 ≠ ok          used·limit 중 하나라도 null 이면 절대 ok 가 아니다
정책 단조성          임계를 엄격하게 하면 ok 가 늘어나지 않는다
정렬 안정            입력 순서가 판정을 바꾸지 않는다
```

찾는 법: ***"이 성질이 뒤집히면 무엇이 실패하는가?"*** 답이 **«아무것도»** 면 거기가
바로 속성이 필요한 자리다. 답이 «컴파일 에러» 면 타입이 이미 지키고 있다.

### ★ 속성도 **통과만으로는 teeth 가 없다** — 변이를 심어 잰다

허브 실측(2026-08-24): 변이 6종 중 **5개가 정확히 해당 속성만** 울렸고(과탐 0),
**1개가 빠져나갔다.**

빠져나간 것: `paceRatio` 의 clamp 제거. 속성이 `Number.isFinite(r)` 만 봐서
`now < startMs` 의 **음수 결과**를 통과시켰다. 무작위 생성에서 0 나눗셈 가지는 사실상
안 밟힌다. → `r >= 0` 을 더했다. **소비 속도는 음수일 수 없다 — 그게 그 값의 의미다.**

> **속성이 「그럴듯」한 것과 「검출력이 있다」는 다른 문장이다.**
> 변이 주입이 아니었으면 그 구멍을 못 봤다.

### 도구·배치

`fast-check` (러너 무관 — bun 전용 커넥터 불요). **부품의 `package.json` 은 건드리지 않는다**:

- `fast-check` 는 **repo 루트의 devDependency** 로
- 테스트는 부품 안 `src/index.property.test.ts`

이유: `part:spec` ②의존은 부품의 `dependencies` 만 보고 ①순수는 구현 파일만 본다.
이 배치면 law-tier 게이트를 흔들지 않으면서 부품을 검사할 수 있다.

### ⚠ 속성 통과가 뜻하지 **않는** 것

「이 부품이 옳다」가 아니라 **「그 축이 안 뒤집힌다」**이다. 미검사 축은 여전히 미검사다.
그리고 속성 자체가 **계측일 수 있다** — 허브 첫 실행의 10건 실패는 코드가 아니라
`fc.date()` 가 기본적으로 `Invalid Date` 를 낸 것이었다. **빨강도 계측이 낸다.**

### 채택은 각 repo 판단이다

허브는 규격과 실물 예시만 준다(`packages/{feature-flags,quota-verdict}/src/index.property.test.ts`).
**`part:spec` 이 속성 테스트를 요구하지 않는다** — 판단 코어 40개에 일괄로 걸면 그날부터
상시 빨간 게이트가 되고, 그건 *"사람을 게이트를 무시하도록 훈련시킨다"*.
필요한 부품에 그 repo 가 붙인다.

## ⚠ 이 규격이 정하지 **않는** 것

- **무엇을 부품으로 만들 것인가** — 그 repo 의 도메인 판단이다. 허브는 권고만 한다
- **정책 필드의 기본값** — 「도메인 판단을 담은 수는 기본값을 두지 않는다」는 규범이지만
  *어느 필드가 도메인 판단인지*는 기계가 못 본다. `UrgencyPolicy.overdueStaysUrgent` 에
  `.default([])` 를 두는 것은 **옳다**
- **SDK·CLI·서버 코어의 형태** — 그건 다른 표면이고, 이 규격의 관할이 아니다
