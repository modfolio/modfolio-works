# 증례 — 빨강이 거짓인 경우 · 침묵하는 실패

멀쩡한 코드가 빨개지는 경우, 성공 문구가 나오는데 일이 안 일어난 경우, 감시자만 안 끝나는 경우, 오탐 수정이 검출력을 지우는 경우.

> **이 파일은 규범이 아니라 증거다.** 규범은 `.claude/rules/agent-evidence.md` 에 있고,
> 그 규칙의 각 항목이 여기 사례를 가리킨다. 2026-08-23 에 `agent-evidence.md` 가
> **137KB** 로 자라 매 턴 30+ repo 에 주입되고 있었기에 **원문 그대로** 분리했다 —
> 요약하면 측정값이 죽는다. 규범은 주입되고, 증거는 필요할 때 읽는다.

## 반대 방향 — **빨강이 거짓일 수 있는 경우** (2026-08-03 athsra 제안, 채택)

여기까지는 전부 *"초록이 왜 거짓인가"* 였다. 반대 축은 비어 있었는데, **형제 세션이
같은 머신에서 동시에 도는 이 환경에서는 그쪽이 더 자주 발생하고 대가가 더 크다** —
오진하면 멀쩡한 코드를 "고치다가" 진짜 회귀를 넣는다.

athsra 실측: 6코어에 **loadavg 250~290**, 그 상태에서 e2e·subprocess 테스트가 무더기로
실패하는데 **실패 대상이 실행마다 바뀐다.**

**4단 진단 — 순서대로. 3단계가 결정적이다.**

| 단계 | 방법 | athsra 실측 |
|---|---|---|
| 1. **격리 재실행** | 그 파일만 단독으로 | 전체 스위트 3 fail → 단독 **23/23 pass**(loadavg 288에서도) |
| 2. **측정 창 확대** | expect timeout 8s → 45s | 그래도 실패 → 부하만으로 설명 안 됨 → 3단계 |
| 3. **baseline 대조** | 내 변경을 `git stash -u` 하고 같은 테스트 | **baseline 에서도 동일 실패** → 내 변경 무관 확정 |
| 4. **CI 를 심판으로** | 통제된 컨테이너(NAS Forgejo) | 두 잡 다 green |

> **1·2단계만으로는 "내가 뭔가 깼나?" 를 못 지운다.** `git stash -u` 로 5분이면 답이
> 나오는데 그전까지는 추론만 반복하게 된다.

**동반 함정 — `quality:all` 은 working tree 를 검사한다.** 백그라운드로 push/게이트를
띄워 놓고 계속 파일을 편집하면 훅이 **반쯤 편집된 트리**를 보고 실패한다. 코드에는
아무 문제가 없다. → 게이트가 도는 동안 트리를 건드리지 않거나, 커밋을 모아 한 번에.

**허브도 같은 밤에 세 번 밟았다**(전부 "빨강이 거짓" 축):

- `quality:all` 이 4회 중 1회 exit 1 → 재현 안 됨. **출력을 `/dev/null` 로 버려 원인
  미상**으로 남았다. 빨간불을 볼 때는 **출력을 남긴 채** 재실행한다.
- 거버넌스가 `test:harness` 안에서만 critical → 단독 실행은 warning. 원인은 **동시에
  돌던 벤치가 저장소 안에 worktree 사본을 만들고 있었던 것**(전수 스캔이 사본을 소스로
  읽었다). 재실행이 아니라 **인과를 찾아야** 갈렸다.
- 로컬 모델 벤치가 시도당 ~300s → 모델이 느린 게 아니라 **VRAM 경합**이었다
  (`/api/ps` 에 다른 프로세스가 6.3GB 보유). 그래서 그 라운드는 이전 라운드와 **비교
  불가**였고, 계측기가 적재 상태를 기록하지 않으면 그 오염이 결과에 남지 않는다.

**한 방향만 보는 대조는 반대편을 침묵으로 덮는다** (athsra 2026-08-04). CI↔로컬 parity 검사가
*"CI 에만 있는 단계"* 만 보고 **«로컬에만 있는 단계»** 는 안 봤다. 반대 방향을 켜자마자
**CI 가 한 번도 안 돌린 로컬 게이트 3개**가 나왔고, 그중 하나는 **전날 실제 버그를 잡은 바로
그 게이트**였다 — 그게 한 머신에서만 살고 있었다. 「census 는 방향을 뒤집으면 유한해진다」와
짝이다: 유한한 쪽을 먼저 만들되, **둘 다** 만들지 않으면 한쪽은 영원히 안 보인다.

**⚠ 그런데 "부하 탓" 으로 끝내면 안 되는 형태가 있다 — 예산 순서** (2026-08-03
atelier-and-folio). 네트워크 의존 테스트가 제목에 *"네트워크 없으면 skip"* 이라 적고
catch → `return` 경로까지 갖췄는데 **그 경로에 한 번도 도달할 수 없었다**:

```ts
// bun 기본 테스트 타임아웃 = 5,000ms
signal: AbortSignal.timeout(8_000)   // ← abort 가 발화하기 전에 테스트가 먼저 죽는다
```

abort 예산이 테스트 예산보다 **길어서** 선언된 graceful skip 이 **죽은 코드**였다.
부하가 낮은 날엔 fetch 가 1초에 끝나 초록, 높은 날에만 빨강 — **"flake 니까 재실행"
으로 넘기기 딱 좋은 형태**이고 실제로 그렇게 분류됐다가, *"제목이 약속한 skip 이 왜
안 걸렸지?"* 를 물어서야 원인이 나왔다.

→ **중첩된 타임아웃은 안쪽이 반드시 더 짧아야 한다.** 그리고 위 4단을 통과해 "부하"
로 분류하기 전에 한 번 더 묻는다: **이 테스트가 선언한 폴백 경로가 실제로 도달
가능한가?** 도달 불가능한 폴백은 빨강을 부하 탓으로 위장한다.

**규칙**: 빨간불에서 결론을 내기 전에 위 4단을 밟는다. 그리고 **재실행으로 넘기지
않는다** — 재현되지 않는 실패는 "없던 일" 이 아니라 **원인 미상**이고, 그렇게 기록한다.

## 세 번째 방향 — **성공 메시지가 있는데 일이 안 일어났다** (2026-08-07 pod:universal)

앞의 둘은 «초록이 거짓» 과 «빨강이 거짓» 이었다. 이건 셋째다 — **초록도 빨강도 아니고,
성공 문구가 있는데 결과가 없다.** 실패의 흔적이 어디에도 안 남아서 가장 오래 산다.

pod:universal 실측(modfolio-pay, `GIT_TRACE=1` 5회 재현):

```
13:47:28  run_command: ssh git@github.com 'git-receive-pack …'   ← git 은 SSH 를 **먼저** 연다
13:47:30  run_command: .githooks/pre-push …                      ← 훅은 그 다음
          … 훅이 13분 (release:gate + a11y + visual + 랜딩) …
          훅 출력: "gate green — push proceeding"    ← 사람은 통과로 읽는다
          git:    **메시지 없이 exit 1**             ← 실패의 흔적이 없다
          원격:   그대로
```

훅이 10분을 넘으면 **먼저 열린 SSH 연결이 유휴로 끊긴다.** 훅 단독 실행은 `exit 0`,
`core.hooksPath=/dev/null` 로는 즉시 성공 — 전송 경로도 게이트도 멀쩡했다.

> **지문**: ① 성공 문구가 출력된다 ② 실패 메시지가 **없다** ③ 원격/외부 상태만 조용히 안 바뀐다.

- **처방(검증됨, 게이트를 하나도 건너뛰지 않는다)**:
  `GIT_SSH_COMMAND="ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=60 -o TCPKeepAlive=yes"`
  keepalive 없이 **5회 실패**, 붙이고 **3회 연속 성공**.
- ⚠ **이 축은 push 만의 것이 아니다.** 「게이트 통과」를 「외부에 도달했다」의 증거로 읽는
  모든 자리가 같다 — 배포·게시·웹훅 발신. modfolio-connect 의 `push:verified` 가 이미
  *"«quality gate 통과» 를 GitHub 에 도달했다는 증거로 읽지 말 것"* 이라고 적어 뒀는데,
  **경고는 옳았고 원인을 몰라 「다시 실행」이 처방이었다.** 원인을 알면 한 번에 끝난다.
- **fleet 노출**(허브 정적 스캔 2026-08-07): pre-push 게이트를 가진 repo **7곳** —
  pay(5스위트) · sign(2) · notify(2) · athsra · connect · design · infra(각 1).
  ⚠ 「무엇을 부르나」이지 「몇 분인가」가 아니다 — 시간은 그 repo 가 잰다.

→ **요구**: 게이트가 통과한 뒤의 «전송/게시/배포» 는 **결과를 따로 확인**한다.
훅 출력이 아니라 **원격 상태**를 본다(`git ls-remote` · 레지스트리 packument · 배포 Version ID).
이 저장소가 이미 아는 «commit≠deployed» 와 같은 축인데, 여기서는 **훅이 성공을 말해서**
더 강하게 믿긴다.

## 네 번째 방향 — **일은 끝났는데 감시자가 모른다** (2026-08-09 허브 실측)

앞의 셋은 «초록이 거짓» · «빨강이 거짓» · «성공 문구인데 안 일어났다» 였다. 이건 넷째다 —
**작업은 정상적으로 끝났고, 그것을 기다리던 것만 영원히 안 끝난다.** 아무 오류도 안 나고
CPU 도 안 쓰므로 며칠이든 산다.

허브 실측: 전파 완료를 기다리는 백그라운드 셸 2개가 **22시간 31분 · 21시간 18분** 돌고
있었다(CPU 누적 각 2초 · 1초). 오너 UI 의 «2 shells still running» 이 유일한 신호였다.

```
until ! pgrep -f "propagate-3610" > /dev/null; do sleep 15; done; echo "전파 종료"; …
                  ↑ 이 문자열이 **이 zsh 자신의 명령줄에 들어 있다**
```

`pgrep -f` 는 전체 명령줄을 매치하므로 **감시자가 자기를 찾는다.** 조건이 영원히 참이다.
실측: `pgrep -af "propagate-3610"` 이 찾은 3개가 **전부 zsh 자신**이었고, 진짜 전파는
로그 마지막 쓰기 기준 **전날 19:00 · 20:23 에 이미 끝나 있었다.**

⚠ **그리고 진단 프로브가 같은 함정에 빠진다** — 원인을 찾으려고 친
`pgrep -af "propagate.ts"` 가 **자기 grep 을 잡아** 한 줄을 돌려줬다. 그 출력은
«전파가 살아 있다» 가 아니라 «내가 보인다» 다. 「0건이면 probe 부터 의심한다」의 거울상:
**1건이어도 그게 나일 수 있다.**

→ **처방**: 프로세스를 기다리는 루프는 **PID 로** 기다린다(`wait $pid` · `kill -0 $pid`).
이름으로 기다려야 하면 자기 제외를 명시한다(`pgrep -f ... | grep -v ^$$`) — 다만 그것도
부모 셸·서브셸까지는 못 거른다. 그리고 **감시 루프에는 상한을 둔다**: 기다리는 대상의
합리적 상한을 넘으면 «완료» 가 아니라 **판정 불능**으로 빠져나온다. 무한 `until` 은
정상 종료와 감시 결함을 구분하지 못한다.

⚠ 이 워크스테이션은 형제 세션이 상시 여럿 도는 곳이라 **이름 매칭이 특히 위험하다** —
남의 프로세스도, 자기 자신도 같은 이름에 걸린다.

## 오탐을 고치다가 **검출력을 0으로** 만들 수 있다 (2026-08-07 허브)

게이트가 오탐을 내면 사람은 그것을 끈다 — 그래서 오탐 수정은 급하다. 그런데 **급하게
고치면 게이트가 죽는다.**

실측: `no-nul-bytes` 의 `BINARY_EXT` 에 `.jar` 가 없어 `gradle-wrapper.jar` 가 오탐이었고,
modfolio-connect 는 그 때문에 그 게이트를 **배선하지 못하고 ACCEPTED 로 돌렸다**(*"영구
빨강인 단계를 push 게이트에 넣으면 사람이 게이트를 무시하도록 훈련된다"*). 제안은
«확장자 목록 대신 git 판정(`ls-files --eol`)» 이었고 **방향은 옳다**(목록은 원리적으로
「이미 아는 것」만 덮는다). 그런데 저장소 밖 최소 재현이 갈랐다:

```
i/-text  gradle-wrapper.jar   ← 걸러야 할 것
i/-text  tainted.md           ← **잡아야 할 진짜 위반인데 같은 판정**
→ git 판정 채택 시: 스캔 대상 clean.ts 뿐 · 위반 0건
```

**git 의 휴리스틱이 곧 "NUL 이 있으면 바이너리"** 라, 이 게이트가 찾으려는 파일을 git 이
먼저 제외한다 — **순환**이다. 채택했으면 게이트는 영원히 초록이면서 아무것도 안 봤다.

→ **요구**: 오탐 수정의 대조쌍에는 **오탐 케이스와 진짜 위반을 함께** 넣는다. 오탐만
넣으면 «사라졌다» 만 보이고, 그 수정이 **검출력까지 지웠는지**는 보이지 않는다.
채택한 형태는 `attr/-text`(**명시 선언**)만 신뢰 + 확장자 목록의 **합집합** — 어느
한쪽으로 대체하지 않는다(①만이면 선언 없는 repo 에서 오탐 재발, ②만이면 목록의 한계 그대로).

## 계약이 producer 를 선언하는데 **아무도 안 쏜다** — 소비자 쪽 얼굴 (2026-08-07 허브)

notify 가 등재한 「게시된 열거값 중 아무도 못 내는 것은 거짓 계약」의 **소비자 판**이다.
그쪽은 «하류가 죽은 분기를 짠다» 였고, 이쪽은 **«하류가 죽은 수신부를 짓는다»** 다.

실측: 허브 `event-wiring` 이 **허브 자신이 소비자인 갭 3건**(`platform.*`)을 P0 로 띄웠고,
그것을 「우리가 안 만들어서」로 읽고 웹훅 수신부를 구현하려 했다. 짓기 전에 쟀더니:

```
계약    "Producer = modfolio-infra · Consumer = the ecosystem control plane"
실물    infra 의 platform.* 발행 코드 0건 · 발행 함수 사용 0건 · emits 전부 []
```

만들었으면 **영원히 아무것도 안 받는 코드**가 되고 갭은 **리포트에서만** 닫혔다.

⚠ 그리고 그 리포트는 *"소비자가 구독을 적기 전에 생산자 실재부터 확인한다"* 고 **이미
조언하고 있었다.** 조언이 **자동화되지 않아** 사람이 두 도구를 손으로 합쳐야 했고,
그러지 않으면 P0 한 숫자가 성격이 다른 둘을 뭉갰다.

→ **요구**: 「소비자가 없다」는 갭은 **생산자 실재로 먼저 가른다.**
```
live            생산자가 실제로 쏘는데 소비자가 없다  → 진짜 갭
contract-ahead  아무도 안 쏜다 → 계약 선행. **갭이 아니다**(계약이 먼저 오는 것은 설계)
undecidable     판정 불능 — 통과로도 위반으로도 접지 않는다
```
판정은 **매니페스트가 아니라 코드**로 한다(계약 유니온 → 발행 코드, 유한한 방향).
허브 실측: 갭 42건 = live **30** · contract-ahead **12**. 종전 방식(매니페스트 `emits`)은
그 필드를 안 쓰는 **29 repo 를 전부 판정 불능**으로 뒀다.
